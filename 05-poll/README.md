# 第 5 节：poll

## 为什么学

poll改掉了select两个最难用的地方：没有1024的上限，传入和返回分开（`events`和`revents`），不用每次重建。
但它没解决O(n)：每次调用仍然把整个数组拷进内核，内核仍然逐个检查。

---

## 要学的内容

1. `struct pollfd { int fd; short events; short revents; }`
2. `events`：`POLLIN`、`POLLOUT`；`revents`里还可能出现`POLLHUP`、`POLLERR`、`POLLNVAL`（这三个不用在events里申请）
3. fd设成负数，poll会跳过这一项，可以用来“删除”而不挪动数组
4. 和select的对比：上限、接口、拷贝量

---

## 任务

### 任务 A：poll版echo服务器

`server_poll.c`：用一个可增长的`struct pollfd`数组（`realloc`）。连接关闭时怎么从数组里删掉？两种做法都试一下：设成-1跳过，或者把最后一个元素挪过来。

用法：`./server_poll [swap|mark]`。`swap`（默认）把最后一项挪过来填空；`mark`只把fd设成-1，新连接优先复用空位，并把末尾的空位收回。

#### 实测结果

- 5000个连接全部建立，抽查100个，回显全部正确，突破了select的1024上限。
- 断开一半后，剩下的连接仍能正常回显；全部断开后，两种模式的`nfds`都回到1，数组里没有残留的已关闭fd。
- 两种删除方式在断开过程中的差别（5000个连接，按先建立的先断开）：

| 当前连接数 | swap 的 nfds | mark 的 nfds |
|---|---|---|
| 100 | 101 | 4835 |
| 200 | 201 | 4935 |
| 300 | 301 | 4955 |

  swap始终紧凑。mark先断开的是低位的连接，高位连接还占着数组末尾，空位收不回来，每轮poll仍要扫描这些空位。

### 任务 B：突破1024

用`many.c`建5000个连接，确认服务器正常（见任务A）。再对比同样1000个空闲连接时select和poll的开销（`active.py`，20000次往返）：

| | 空闲 CPU | 20000次往返用时 | 平均延迟 |
|---|---|---|---|
| select，几乎没有空闲连接（第4节） | | | 86.7 µs |
| select，1000个空闲连接 | 0.0 | 3.48 秒 | 173.9 µs |
| poll，1000个空闲连接 | 0.0 | 3.34 秒 | 167.2 µs |

- 两者空闲时CPU都是0：睡在系统调用里，没事件就不占CPU。
- 1000个空闲连接让延迟从86.7 µs涨到约170 µs，多出的约80 µs是内核每轮检查这些fd的开销，select和poll都一样。
- poll比select快约4%，但只测了一轮，差距太小，不能当稳定结论。poll省了重建`fd_set`，但每轮要拷贝约8 KB的`pollfd`数组（select只拷128字节），两者基本抵消。
- 没有测5000个空闲连接下的延迟，“随连接数线性增长”只是推断，不是这一节的实测结论。

## 写之前先想清楚

1. 对方断开时，`revents`里可能是`POLLIN`（read返回0），也可能带`POLLHUP`。两种都要处理吗？

   > **答：** 要。对方正常`close`时一般表现为`POLLIN`，`read`返回0；连接被重置或双方都关闭时，可能带`POLLHUP`、`POLLERR`。
   > 如果只检查`POLLIN`，就可能漏掉只带`POLLHUP`/`POLLERR`的情况，这个fd一直留在数组里，`poll`每轮都立刻返回，变成空转。
   > 所以代码里只要`revents`非0（先排除`POLLNVAL`），就统一交给`read`判断：返回正数是数据，0是对方关闭，-1是错误。

2. 把最后一个元素挪过来填空，遍历`revents`时要注意什么？（提示：刚挪过来的那个还没检查）

   > **答：** 正着遍历会漏掉被挪过来的那一项：删除第`i`项后，最后一项被放到位置`i`，循环`i++`直接跳过了它，它这一轮的事件就没处理。
   > 倒着遍历（从`nfds-1`到1）就不会：被挪到位置`i`的最后一项，已经在前面被检查过了。循环条件写`i >= 1`，不能删掉`fds[0]`（listenfd）。

3. poll和select的O(n)是同一个n吗？select的n是最大fd号，poll的n是数组长度，什么时候差别大？

   > **答：** 不是同一个。select内核要扫描`[0, maxfd]`，poll扫描`nfds`项。
   > - 连接少但fd号很大（比如进程先开了很多文件或连接再关掉，只剩几个连接）：select仍要扫到`maxfd`，poll只扫实际项数。
   > - 连接的fd号都很小、很紧凑：两者差不多。
   > - poll自己也会虚高：mark模式下空位留在数组里，实测只剩100个连接时`nfds`仍有4835，poll照样要扫描这些空位。

## 自查方法

- 5000个连接正常回显。
- 连接反复建立、断开后，数组里没有残留的已关闭fd（打印数组长度确认）。

## 结论

1. **poll解决了select的1024上限，没有解决O(n)。** 数组按项数存放，只受`ulimit -n`和内存限制；但每轮调用仍要把整个数组拷进内核，内核和用户态都要线性扫描。连接越多、活跃的越少，浪费越大。
2. **`events`和`revents`分开**，数组不用像`fd_set`那样每轮重建，代码比select简单。
3. **swap删除紧凑，mark删除省挪动但会留空洞。** mark必须配合空位复用和末尾收缩，否则数组只增不减。
4. 想把开销降到只和就绪连接数有关，需要epoll（下一节）。

## 踩坑

1. **`fds = realloc(fds, ...)`：** realloc失败返回NULL，原指针丢失造成泄漏。要用临时变量接住，确认非NULL再赋值。
2. **`realloc`后数组可能搬家：** 之前保存的`&fds[i]`全部失效，只用下标访问。
3. **新追加项的`revents`不清零：** realloc出来的内存是随机值，可能被误当成有事件。
4. **正着遍历配合“挪最后一项”删除：** 会漏掉被挪过来的那一项。要倒着遍历。
5. **只检查`POLLIN`：** 漏掉`POLLHUP`/`POLLERR`，连接残留并造成空转。
6. **删除了`fds[0]`：** listenfd被挤掉，服务器不再接受新连接。倒着遍历只到1。
7. **mark模式不复用空位、不收回末尾：** 数组只增不减，每轮扫描的项越来越多。
8. **编辑器里`accept4`报隐式声明：** 编辑器没读到CMake里的`_GNU_SOURCE`，实际编译没有警告，可以忽略。

## 最佳实践

1. 数组第0项固定放listenfd，客户端从1开始，遍历时跳过第0项。
2. 用swap删除并倒着遍历；若用mark，必须复用空位并收回末尾空位。
3. `realloc`用临时变量接返回值，增长时容量翻倍，全程用下标，不保存元素指针。
4. 只要`revents`非0（先单独处理`POLLNVAL`），就交给`read`判断，不依赖具体是哪个事件位。
5. 跑大量连接前，服务器和客户端的终端都要`ulimit -n`调高。
