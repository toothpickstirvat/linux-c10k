# 第 2 节：一个连接一个进程 / 一个线程

## 为什么学

第1节的服务器一次只能服务一个人。最直接的办法是每来一个连接就开一个进程或线程去处理。这个模型写起来最简单，
早期的Apache就是这样。它的问题就是C10K问题的起点：**连接数上万时，进程/线程本身的开销压垮了机器。**

---

## 要学的内容

1. `fork`：父进程继续`accept`，子进程处理连接；父子进程各自要关掉不用的fd
2. 僵尸进程：子进程退出后父进程不`waitpid`，会留下僵尸；用`SIGCHLD`处理函数回收
3. `pthread_create` + `pthread_detach`：线程退出后自动回收
4. 每个线程的开销：栈（本机默认8MB虚拟内存）、内核调度结构、上下文切换

---

## 任务

### 任务 A：fork版

`server_fork.c`：每accept一个连接就`fork`，子进程跑第1节的echo循环，结束后`exit`。父进程用`SIGCHLD`回收子进程。

### 任务 B：线程版

`server_thread.c`：每accept一个连接就`pthread_create`，线程函数跑echo循环，`pthread_detach`让它自己回收。
注意：fd怎么传给线程函数？（传`&connfd`有什么问题？）

### 任务 C：量一量开销

写一个小客户端`many.c`：建立N个连接，全部保持不关，然后`pause()`。对线程版服务器：

- N = 1000 时，用 `ps -o pid,nlwp,vsz,rss -p <pid>`看线程数、虚拟内存、实际内存。
- 算一算：每个线程的VSZ和RSS各多少？为什么两者差这么多？
- 用`ulimit -s 256`启动服务器后再看，或者用`pthread_attr_setstacksize`把栈调小。

#### 实测结果（线程版，1000 个连接）

| | NLWP | VSZ | RSS |
|---|---|---|---|
| 空闲，0 个连接 | 1 | 2.7 MB | 1.7 MB |
| 默认栈 `ulimit -s 8192` | 1001 | **7.8 GB** | 10.0 MB |
| `ulimit -s 256` | 1001 | **257 MB** | 10.0 MB |

- **每个线程 VSZ 约 8 MB**：就是线程栈（加一个 4KB 保护页），大小取自 `ulimit -s`。
- **每个线程 RSS 约 8.4 KB**：`(10200 − 1764) / 1000`。echo 线程只用到很浅的一层栈（`buf[1024]` 加几层调用），
  只碰了一两页，所以实际物理内存很小。
- **栈调到 256 KB 后 VSZ 降了 32 倍，RSS 几乎不变**：证明默认 8 MB 栈绝大部分只是预约地址、没被用到。
  RSS 决定于实际碰过的页数，与栈预约大小无关。

## 写之前先想清楚

1. fork后，子进程要不要关listenfd？父进程要不要关connfd？不关会怎样？（提示：客户端断开后连接为什么不真正关闭）

   > **答：** 都要关。fork 把 fd 表整个复制了一份，父子进程**都**持有 listenfd 和 connfd，各自要关掉用不到的：
   > 子进程关 listenfd，父进程关 connfd。
   > - **父进程不关 connfd**：实测把父进程的 `close(connfd)` 注释掉，连 3 个客户端，父进程的 socket fd 变成 4、5、6
   >   一路累积（每连接泄漏一个 fd），客户端断开后连接全卡在 `CLOSE-WAIT`：
   >   ```
   >   客户端 127.0.0.1:48676 已连接（fd=4）
   >   客户端 127.0.0.1:48690 已连接（fd=5）
   >   客户端 127.0.0.1:48694 已连接（fd=6）
   >   3 CLOSE-WAIT    ← 对方发了 FIN，我方始终没 close
   >   ```
   >   内核里每个 socket 有一个引用计数，父子都持有时计数是 2。子进程 `close` 或退出后计数降到 1，
   >   因为父进程还占着，**这个连接不会真正关闭**，FIN 发不出去，连接一直停在 `CLOSE-WAIT`。fd 用完后 `accept` 会返回 `EMFILE`。
   > - **子进程不关 listenfd**：危害小一些，但子进程会一直占着监听 socket；而且它继承了 listenfd，逻辑上也不该由它持有。

2. 线程版里，一个线程`close(fd)`之后，fd号被下一个`accept`复用。如果别的线程还拿着旧的fd号在读，会读到谁的数据？

   > **答：** 会读到新连接的数据，或者写到新连接上——**串线了**。因为所有线程共用一张 fd 表，fd 号一关就立刻可能被
   > 新连接复用。这就是为什么线程版里 connfd 必须由处理它的线程自己关，主线程**不能**像 fork 版那样创建完线程就关。
   > 这类 bug 很隐蔽：平时线程读写很快，不会撞上；只有连接密集、时序恰好时才偶发。要靠规范（fd 归属单一、谁用谁关）
   > 来避免，而不是靠运气。本节的 data race（传 `&connfd`）是同一类问题，用 ThreadSanitizer 能直接报出来。

3. 8 MB 栈 × 1 万个线程 = 80 GB，本机只有15 GB内存，为什么还可能开得出来？那真正的限制是什么？

   > **答：** 因为 80 GB 是 **VSZ（虚拟地址空间）**，不是物理内存。`pthread_create` 用 `mmap` 给每个线程**预留** 8 MB
   > 地址，内核并不马上分配物理页；线程真正读写到某一页时才缺页、才分配。echo 线程只用一两页，所以 1 万个线程的 RSS
   > 也就 ~100 MB。真正的限制是：
   > - **线程数上限**：`threads-max`（本机 98902）、`ulimit -u`（本机 49451）、`pid_max`（本机 4194304）。
   > - **虚拟内存映射数**：每个线程栈是一个 VMA，受 `vm.max_map_count`（本机 1048576）限制。
   > - **内存提交策略**：本机 `vm.overcommit_memory=0`（启发式允许超额），所以 80 GB 虚拟空间能开出来；若设成 2（严格），
   >   预留就会失败。把栈调小（`ulimit -s` 或 `pthread_attr_setstacksize`）能大幅降低 VSZ。
   > - **调度开销**：1 万个线程大多阻塞在 `read`，数据一到就要唤醒、切换上下文、读完再睡，线程越多，花在切换上的 CPU 越多。
   >   这才是"一个连接一个线程"真正扛不住 C10K 的原因，第 8 节会把各模型的这项开销放在一起比。

## 两种信号，分别解决什么问题

| 信号 | 解决什么 | 怎么做 |
|---|---|---|
| `SIGPIPE` | 对方断开后还 write，默认动作**杀死进程**（fork 版杀一个子进程，线程版杀整个服务器） | `signal(SIGPIPE, SIG_IGN)`，之后 write 返回 `EPIPE` |
| `SIGCHLD` | fork 版子进程退出后，父进程要**及时回收**，否则堆积僵尸占满进程号 | `sigaction` 注册处理函数，里面循环 `waitpid(-1, NULL, WNOHANG) > 0` |

**为什么 SIGCHLD 要用信号，而不是在主循环里 `wait`？** 父进程绝大多数时间阻塞在 `accept`，不能同时阻塞在 `wait` 上；
而在每次 `accept` 返回后才 `WNOHANG` 回收又不及时（没有新连接时退出的子进程会一直是僵尸）。信号是一种**异步通知**：
子进程一退出，内核就打断父进程去执行处理函数，回收完再回来。代价是 `accept` 会被打断返回 `EINTR`（需处理或用 `SA_RESTART`）、
信号不排队（处理函数要循环回收）、处理函数随时可能插入执行（要存/恢复 `errno`，只能用异步信号安全函数，不能用 `printf`）。

**子进程能不能自己回收自己？** 不能。`SIGCHLD` 是发给**父进程**的；`waitpid` 只能等自己的子进程、不能等自己；
进程退出后也执行不了任何代码。僵尸就是内核替父进程保存的那份退出状态，只有父进程 `waitpid` 取走才会清除。
如果完全不关心退出状态，可以 `signal(SIGCHLD, SIG_IGN)` 或 `SA_NOCLDWAIT`，让内核直接清理、不留僵尸；
但真实服务器（如 nginx master 判断 worker 是否崩溃）通常需要退出状态，所以还是要 `waitpid`。
后面第 4 节起还有更干净的做法：用 `signalfd` 把信号变成 fd，和 socket 一起交给 epoll，彻底不用信号处理函数（第 9 节的 `timerfd` 同理）。

## fd 号为什么总是从最小的空闲号开始

内核分配 fd 时，总是取**当前进程**里编号最小的空闲 fd。

- **fork 版两个子进程的 connfd 都是 4**：父进程每次 fork 后都 `close(connfd)`，自己手里永远只有 0/1/2/3，下次 `accept`
  又拿到 4。两个子进程虽然都用 4，但各自有独立的 fd 表，4 指向不同的 socket（`ls -l /proc/<pid>/fd` 里 inode 不同），互不影响。
- **线程版的 connfd 是 4、5、6 递增**：所有线程共用一张 fd 表，连接 A 还占着 4 时，连接 B 只能拿 5。
- fd 不是"连接的编号"，只是进程 fd 表里的下标，指向内核的一个 socket 对象。

## 结论

1. **进程/线程-per-connection 的瓶颈不是物理内存，是线程数上限和调度开销。** 内存靠虚拟地址预留 + 按需缺页，撑得住；
   但上万个线程的创建、切换、唤醒开销压垮 CPU。这就是 C10K 的起点。
2. **fork 版 fd 表独立，线程版 fd 表共享。** 由此派生出两套完全不同的 fd 管理规则和 bug 类型。
3. **多进程要先 `fflush` 再 fork**，多线程要注意传参的生命周期、共享 fd 的归属，两者都要忽略 SIGPIPE。

## 踩过的坑

1. **子进程处理完不 `exit`：** 继续往下走回到外层 `accept`，而它已 `close(sockfd)`，`accept` 返回 `EBADF` 死循环刷屏、占满 CPU。
2. **`waitpid` 循环条件写成 `!= 0`：** 最后一个子进程回收后 `waitpid` 返回 -1（`ECHILD`），-1 也为真，父进程死循环卡在处理函数里，再也回不到 `accept`。要用 `> 0`。
3. **fork 前不 `fflush(stdout)`：** 重定向到文件时 stdout 全缓冲，父进程缓冲区随 fork 被复制，每个子进程 `exit` 时重复写一遍。
   换 `_exit` 又会丢掉子进程自己的输出。正解是 fork 前 `fflush`，或 `setvbuf` 设行缓冲。
4. **线程版传 `&connfd` / `&pclient`：** 传的是主线程栈上同一个变量的地址，下一轮 `accept` 就覆盖它，导致两个线程服务同一连接、
   另一连接无人服务（压测 200 个连接时 16 个无回显）。要直接传 `malloc` 出来的指针本身（它每轮都是新地址）。
5. **线程版不 `close(connfd)`：** 所有连接卡 `CLOSE-WAIT`、fd 持续泄漏（压测后 200 个 `CLOSE-WAIT`、202 个 fd）。要由线程在末尾统一关。
6. **`n == 0` 直接 `return` 跳过清理：** 正常断开是最常见路径，却漏掉了 `close` + `free`，几乎每个连接都泄漏。三种退出都要走到统一清理处。
7. **不 `pthread_detach`：** 既不 join 也不 detach 的线程退出后，栈和描述符不回收，是线程版的"僵尸"。

## 最佳实践

1. fork 版：子进程处理完必须 `exit`；`SIGCHLD` 处理函数循环 `waitpid(...) > 0`、存/恢复 `errno`、只用异步信号安全函数；fork 前 `fflush`。
2. 线程版：传参用 `malloc` 的独立内存（谁用谁 `free`）；connfd 由处理线程自己 `close`；创建后立刻 `pthread_detach`；主线程不碰已交出的 fd。
3. 两者都在 `main` 开头 `signal(SIGPIPE, SIG_IGN)`。
4. pthread 系列函数不设置 `errno`，错误码是返回值，用 `strerror(err)` 打印。
5. 每个 fd 只在一个确定的地方关闭；fd 归属单一。
6. 想压低 per-connection 内存，调小线程栈（`ulimit -s` 或 `pthread_attr_setstacksize`），能大幅降 VSZ。
